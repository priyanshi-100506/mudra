# Evaluation

15 fixture pages, ground truth, and a harness that measures MUDRA's real
detection modules against them.

```sh
cd extension && npm run eval
```

One command. It writes `results.json`, which is committed. "Run it yourself"
is the strongest answer to a challenged number, so both the ground truth and
the results are in the repository rather than described in a slide.

---

## Everything here is synthetic

No real person's data appears anywhere in this repository.

Every identifier in the fixtures is fake and generated by
`build-fixtures.mjs`. The valid ones are constructed to **pass** their real
checksums and the decoys are constructed to **fail** them, and both properties
are asserted at generation time — a fixture cannot silently become the wrong
kind of test case. Names, addresses and email domains are invented
(`example.test`).

The fixtures and `ground-truth.json` are generated together, from the same
constants. A ground-truth file maintained by hand beside hand-written fixtures
drifts within a week: someone edits a number in a page, the expectation still
holds the old one, and the harness starts reporting a recall figure that
measures nothing.

---

## The decoy column

This is the column worth reading first, and it is the one a regex-based
detector cannot produce.

Five look-alike values that match the shape of an identifier and fail its
checksum:

| Decoy | Looks like | Why it is not |
|---|---|---|
| 12-digit order number | Aadhaar | fails Verhoeff |
| 12-digit invoice number | Aadhaar | fails Verhoeff |
| 16-digit ticket number | payment card | fails Luhn |
| 16-digit batch number | payment card | fails Luhn |
| PAN-shaped warehouse SKU | PAN | *nothing — see below* |

A false positive here is not a harmless over-reach. A sealed order number is a
field the planner can no longer read, so the agent cannot complete a task that
depends on it. Over-redaction has a cost, and pretending otherwise is how a
privacy layer ends up switched off.

**Measured: 1 false positive in 5.** The one is the PAN-shaped SKU.

PAN carries no checksum, so shape alone cannot separate a real PAN from any
other ten-character alphanumeric code. Constraining the fourth character to
the holder-type letters was tried and reverted: the letter set is not
something we can be certain of, and getting it wrong means failing to seal a
real PAN. A sealed SKU costs one unreadable field; an unsealed PAN is the
failure this project exists to prevent. The asymmetry decides it, and the
false positive stays on the record.

## What the harness measures, and how

Detection is scored on whether a value was **sealed**, not on whether it
appears in the outbound body.

That distinction matters more than it sounds, and getting it wrong produced
two earlier versions of this harness that reported flattering nonsense:

- The scene graph carries no `value` field at all, so *every* value on every
  page is absent from the payload. Scoring on absence gives a perfect result
  to a detector that does nothing.
- A value the perception layer never captured cannot be scored either way. A
  decoy sitting in a table cell is never in the PageIR, so the detector was
  never asked about it. Those are reported as `notObserved` rather than
  counted as successes.

So: a value counts as detected when it was present in the captured PageIR and
the redactor sealed it into a reference or stripped it from a text snippet. A
decoy counts as a false positive when it was present and sealed.

Rows the pipeline cannot currently produce are reported as `not-run`, never as
zero. A zero says "we looked and found nothing"; not-run says "we did not
look".

## Current results

From the committed `results.json`. Conditions are recorded with the numbers,
because a number without its conditions invites the one question that cannot
be answered on stage.

**Environment:** Apple M3, 8 cores, 8 GB RAM, macOS (Darwin 25.5.0 arm64),
Node v24.2.0, Chrome 153. Text pipeline measured in JSDOM.

| Metric | Value |
|---|---|
| Recall (text pipeline) | **100%** (7/7) |
| Precision | **87.5%** |
| F1 | **93.3%** |
| Decoy false positives | **1 / 5 (20%)** |
| Leaks after redaction | **0** |
| Canaries escaped | **0** of 3 per observation |
| Local pipeline p50 / p95 | **7.9 ms / 59.0 ms** |
| Payload per observation p50 / p95 | **474 B / 896 B** |
| Peak heap | **123.6 MB** |

### Not yet run

Six fixtures — five image-only and the statue decoy — require
`version-RFB-320.onnx`, which is not yet in `extension/public/models/`. Their
rows read `not-run`. They are **not** reported as zeros, and the recall figure
above is explicitly scoped to the text pipeline rather than presented as a
whole-system number.

Still to be measured once the weights land:

- face detection recall, and the statue false-positive case
- image-only PII recall, including the Devanagari fixture
- first-load cost, separately from steady state
- visual-pass latency
- the payload-versus-raw-screenshot ratio, which needs a real capture

First-load and steady-state timings are kept apart, the same way the panel
keeps `warmupMs` apart from its stage times. Both are honest; averaging them
is not, because they answer different questions.

## What this run already found

The harness earned its place before producing a single reportable number: it
found a real defect in the product.

`shared/redact.ts` carried its own copies of the Aadhaar, PAN and card
patterns, and **the Aadhaar copy had no Verhoeff check**. Every 12-digit order
and invoice number on a page was being sealed as an identity document, and the
planner could then not read the field at all. Two detectors is one too many,
and the looser one wins by default because it fires first. It now delegates to
the single validated detector, and the decoy false-positive rate fell from
5/5 to 1/5.

## Files

| File | |
|---|---|
| `build-fixtures.mjs` | generates the fixtures and ground truth together |
| `fixtures/` | 15 pages: 5 DOM PII, 5 image-only PII, 5 decoys |
| `ground-truth.json` | expected PII and decoys per fixture |
| `run-eval.ts` | the harness |
| `harness.spec.ts` | entry point for `npm run eval` |
| `results.json` | the committed result of the last run |

The harness is deliberately **not** part of the test suite. A test asserts;
this measures. Keeping them apart means a disappointing number fails nothing,
which is the only way the numbers stay honest.
